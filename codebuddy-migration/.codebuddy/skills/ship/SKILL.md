# Ship：全自动发布工作流

你正在运行 `/ship` 工作流。这是一个**非交互的全自动**工作流。不要在任何步骤询问确认。用户说了 `/ship`，意味着执行它。一路运行到底，最后输出 PR URL。

**只停下来：**
- 在基础分支上（中止）
- 无法自动解决的合并冲突
- 测试失败
- 预着陆审查发现需要用户判断的 ASK 项
- 需要 MINOR 或 MAJOR 版本升级
- TODOS.md 不存在且用户想创建

**永远不停下来：**
- 未提交的更改（始终包含）
- 版本升级选择（自动选 MICRO 或 PATCH）
- CHANGELOG 内容（从 diff 自动生成）
- 提交消息审批
- 自动可修复的审查发现

---

## Step 1：预检

1. 检查当前分支。如果在基础分支上，**中止**。

2. 运行 `git status`。未提交的更改始终包含。

3. 运行 `git diff` 和 `git log` 了解正在发布什么。

4. 检查审查就绪状态：
   - 如果工程审查未通过且无先前覆盖，提问是否继续。
   - 如果用户选择继续，持久化决策以便后续 `/ship` 跳过。

---

## Step 2：合并基础分支（测试之前）

```bash
BASE=$(gh pr view --json baseRefName -q .baseRefName 2>/dev/null || echo "main")
git fetch origin $BASE && git merge origin/$BASE --no-edit
```

合并冲突：简单的自动解决。复杂的停下来展示。

---

## Step 2.5：测试框架引导

检测项目的测试框架。如果未找到测试框架，提问是否引导一个。

---

## Step 3：运行测试（在合并后的代码上）

并行运行项目的测试套件。任何测试失败则**停下**。

---

## Step 3.4：测试覆盖率审计

100% 覆盖是目标。

**1. 追踪每个变更的代码路径：**
读取每个变更文件。追踪数据流经每个分支。

**2. 映射用户流程、交互和错误状态。**

**3. 对照现有测试检查每个分支。**

**4. 输出 ASCII 覆盖率图表：**

```
代码路径覆盖
===========================
[+] src/services/billing.ts
    ├── processPayment()
    │   ├── [★★★ 已测试] 快乐路径 + 卡片拒绝 + 超时
    │   └── [缺口]       网络超时 — 无测试
```

**5. 为未覆盖路径生成测试。**

---

## Step 3.5：预着陆审查

审查 diff 中测试无法捕获的结构性问题。

1. 读取审查检查清单。
2. 两遍审查：
   - **第 1 遍（关键）：** SQL 安全、竞态条件、LLM 输出信任边界
   - **第 2 遍（信息性）：** 所有其余类别

3. 分类：AUTO-FIX 或 ASK。
4. 自动修复所有 AUTO-FIX 项。
5. ASK 项合并为一次提问。
6. 如果有修复：提交，告诉用户重新运行 `/ship`。

---

## Step 4：版本升级（自动决策）

1. 读取当前 `VERSION` 文件（4 位格式：`MAJOR.MINOR.PATCH.MICRO`）。
2. 根据 diff 自动决定：
   - **MICRO**：< 50 行变更
   - **PATCH**：50+ 行变更
   - **MINOR**：**提问**——仅用于重大功能
   - **MAJOR**：**提问**——仅用于里程碑或破坏性变更
3. 写入新版本。

---

## Step 5：CHANGELOG（自动生成）

1. 从分支上**所有提交**自动生成条目。
2. 分类为：Added、Changed、Fixed、Removed。
3. 格式：`## [X.Y.Z.W] - YYYY-MM-DD`

---

## Step 5.5：TODOS.md（自动更新）

1. 检查 TODOS.md 是否存在。不存在则提问是否创建。
2. 检查结构和组织。
3. 检测已完成的 TODO（保守——只在 diff 中有明确证据时标记）。
4. 移动已完成项到 Completed 部分。

---

## Step 6：提交（可二分的块）

1. 将变更分组为逻辑提交。
2. 提交顺序：基础设施 → 模型/服务 → 控制器/视图 → VERSION + CHANGELOG + TODOS。
3. 每个提交独立有效。
4. 消息格式：`<type>: <summary>`。

---

## Step 7：推送

```bash
git push -u origin <branch-name>
```

---

## Step 8：创建 PR

```bash
gh pr create --base <base> --title "<type>: <summary>" --body "..."
```

PR 正文包含：
- 摘要（CHANGELOG 要点）
- 测试覆盖
- 预着陆审查
- 设计审查
- TODOS
- 测试计划

**输出 PR URL** — 用户看到的最终输出。

---

## 重要规则

- **永远不跳过测试。** 失败则停止。
- **永远不跳过预着陆审查。**
- **永远不强制推送。**
- **永远不要询问确认**（MINOR/MAJOR 版本升级和 ASK 审查项除外）。
- **4 位版本格式。**
- **为可二分性拆分提交。**
- **TODOS 完成检测必须保守。**
- **目标：用户说 `/ship`，下一个看到的是 PR URL。**
