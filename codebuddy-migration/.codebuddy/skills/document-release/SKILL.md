# 文档发布：发布后文档更新

你正在运行 `/document-release` 工作流。此工作流在 `/ship` 之后（代码已提交，PR 已存在或即将存在）但在 PR 合并之前运行。你的工作：确保项目中每个文档文件准确、最新、且以友好的面向用户的风格编写。

你大部分是自动化的。直接做明显的事实性更新。只在有风险或主观决策时停下来询问。

**只停下来询问：**
- 有风险/可疑的文档变更（叙述、哲学、安全、删除、大范围重写）
- VERSION 升级决策（如果尚未升级）
- 要添加的新 TODOS 项
- 跨文档的叙述性矛盾

**永远不停下来：**
- 明显来自 diff 的事实性修正
- 向表格/列表添加项
- 更新路径、计数、版本号
- 修复过时的交叉引用
- CHANGELOG 措辞润色
- 标记 TODOS 完成
- 跨文档事实性不一致

**永远不做：**
- 覆盖、替换或重新生成 CHANGELOG 条目——只润色措辞，保留所有内容
- 不询问就升级 VERSION——始终先询问
- 对 CHANGELOG.md 使用全文覆写——始终使用精确匹配的局部编辑

## Step 1：预检与 Diff 分析

1. 检查当前分支。如果在基础分支上，**中止**："你在基础分支上。从功能分支运行。"

2. 收集变更上下文：

```bash
BASE=$(gh pr view --json baseRefName -q .baseRefName 2>/dev/null || echo "main")
git diff $BASE...HEAD --stat
git log $BASE..HEAD --oneline
git diff $BASE...HEAD --name-only
```

3. 发现仓库中所有文档文件：

```bash
find . -maxdepth 2 -name "*.md" -not -path "./.git/*" -not -path "./node_modules/*" | sort
```

4. 将变更分类为：新功能、行为变更、移除功能、基础设施。

5. 输出简要摘要："分析 N 个文件变更，跨 M 个提交。发现 K 个文档文件需要审查。"

---

## Step 2：逐文件文档审计

读取每个文档文件并与 diff 交叉引用：

**README.md：**
- 是否描述了 diff 中可见的所有功能？
- 安装/设置说明是否与变更一致？

**ARCHITECTURE.md：**
- ASCII 图表和组件描述是否匹配当前代码？
- 保守——只更新 diff 明确矛盾的内容。

**CONTRIBUTING.md — 新贡献者冒烟测试：**
- 作为全新贡献者走一遍设置说明。
- 列出的命令是否准确？

**项目说明文件（如 CLAUDE.md）：**
- 项目结构部分是否匹配实际文件树？
- 列出的命令和脚本是否准确？

分类为：
- **自动更新** — 明显由 diff 保证的事实性修正
- **询问用户** — 叙述性变更、大范围重写

---

## Step 3：应用自动更新

直接做所有清晰的事实性更新。
每个修改文件输出一行摘要。

---

## Step 4：询问有风险的变更

对每个有风险的更新，单独提问：
- 上下文：项目、分支、哪个文档文件
- 具体的文档决策
- 推荐 + 原因
- 选项包括 C) 跳过——保持原样

---

## Step 5：CHANGELOG 措辞润色

**关键——永远不要覆盖 CHANGELOG 条目。**

规则：
1. 先读取整个 CHANGELOG.md。
2. 只修改现有条目内的措辞。永远不删除、重排或替换条目。
3. 永远不从头重新生成条目。
4. 如果条目看起来不对，先提问。

如果 CHANGELOG 在此分支未修改：跳过此步骤。

润色标准：
- 卖点测试：用户读到每条会想"哦不错，我要试试"吗？
- 以用户现在能**做什么**开头——不是实现细节。
- 标记读起来像 commit message 的条目并改写。
- 内部/贡献者变更放在独立的"### 贡献者"子部分。

---

## Step 6：跨文档一致性与可发现性检查

1. README 的功能列表是否匹配项目说明文件描述的？
2. 所有文档是否版本号一致？
3. **可发现性：** 每个文档文件是否从 README 或项目说明文件可达？
4. 标记任何跨文档矛盾。

---

## Step 7：TODOS.md 清理

如果 TODOS.md 不存在，跳过。

1. **已完成但未标记的项：** 与 diff 交叉引用。
2. **需要更新描述的项：** 提问确认。
3. **新推迟的工作：** 检查 diff 中的 TODO/FIXME/HACK 注释。

---

## Step 8：VERSION 升级问题

**关键——永远不要静默升级 VERSION。**

1. 如果 VERSION 不存在：静默跳过。
2. 检查 VERSION 是否已在此分支修改。
3. 如果未升级：提问。推荐跳过（文档变更很少需要版本升级）。
4. 如果已升级：检查是否覆盖了全部变更范围。

---

## Step 9：提交与输出

**空检查：** 如果没有文档文件被修改，输出"所有文档已是最新。"并退出。

**提交：**
1. 按名称暂存修改的文档文件（永远不用 `git add -A`）。
2. 创建单个提交。
3. 推送。

**文档健康摘要（最终输出）：**

```
文档健康状态：
  README.md       [状态] ([详情])
  ARCHITECTURE.md [状态] ([详情])
  CONTRIBUTING.md [状态] ([详情])
  CHANGELOG.md    [状态] ([详情])
  TODOS.md        [状态] ([详情])
  VERSION         [状态] ([详情])
```

状态：已更新 / 当前 / 措辞润色 / 未升级 / 已升级 / 跳过

---

## 重要规则

- **先读后改。** 修改前始终读取文件完整内容。
- **永远不覆盖 CHANGELOG。** 只润色措辞。
- **永远不静默升级 VERSION。** 始终询问。
- **明确说明变更内容。** 每次编辑一行摘要。
- **通用启发式，不针对特定项目。**
- **可发现性很重要。** 每个文档文件应从 README 可达。
