# QA 测试方法论

## 测试模式

### 差异感知模式（在特性分支上且无 URL 时自动启用）

这是开发者验证自己工作的**主要模式**。当用户在特性分支上运行 `/qa-report` 或 `/qa-fix` 且未提供 URL 时，自动：

1. **分析分支差异**，了解什么发生了变化：
   ```bash
   git diff main...HEAD --name-only
   git log main..HEAD --oneline
   ```

2. **从变更文件中识别受影响的页面/路由**：
   - 控制器/路由文件 → 对应的 URL 路径
   - 视图/模板/组件文件 → 渲染它们的页面
   - 模型/服务文件 → 使用这些模型的页面（检查引用它们的控制器）
   - CSS/样式文件 → 包含这些样式表的页面
   - API 端点 → 直接测试：`$B js "await fetch('/api/...')"`
   - 静态页面（markdown、HTML）→ 直接导航

3. **检测运行中的应用** — 检查常见本地开发端口：
   ```bash
   $B goto http://localhost:3000 2>/dev/null && echo "Found app on :3000" || \
   $B goto http://localhost:4000 2>/dev/null && echo "Found app on :4000" || \
   $B goto http://localhost:8080 2>/dev/null && echo "Found app on :8080"
   ```
   如果没有找到本地应用，检查 PR 或环境中是否有预发布 URL。如果什么都不行，询问 Boss 提供 URL。

4. **测试每个受影响的页面/路由：**
   - 导航到页面
   - 截图
   - 检查控制台错误
   - 如果变更是交互性的（表单、按钮、流程），端到端测试交互
   - 操作前后使用 `snapshot -D` 验证变更是否达到预期效果

5. **与 commit 消息和 PR 描述交叉对照**，理解*意图*——变更应该做什么？验证它确实做到了。

6. **检查 TODOS.md**（如果存在），查找与变更文件相关的已知 bug 或问题。如果一个 TODO 描述了这个分支应该修复的 bug，将其加入测试计划。如果在 QA 过程中发现了 TODOS.md 中没有的新 bug，在报告中记录。

7. **报告发现**，限定在分支变更范围内：
   - "测试的变更：此分支影响了 N 个页面/路由"
   - 每个页面/路由：能正常工作吗？截图证据。
   - 相邻页面有无回归？

**如果用户在差异感知模式中提供了 URL：** 使用该 URL 作为基础，但仍然将测试范围限定在变更文件。

### 完整模式（提供 URL 时的默认模式）
系统化探索。访问每个可达页面。记录 5-10 个有充分证据的问题。生成健康评分。根据应用大小需要 5-15 分钟。

### 快速模式（`--quick`）
30 秒冒烟测试。访问首页 + 前 5 个导航目标。检查：页面加载？控制台错误？断链？生成健康评分。不做详细问题文档。

### 回归模式（`--regression <baseline>`）
运行完整模式，然后加载之前运行的 `baseline.json`。比较：哪些问题修复了？哪些是新的？评分差异？在报告中附加回归部分。

## 阶段 1：初始化

1. 找到 browse 二进制（参见 browse 技能的 Setup 部分）
2. 创建输出目录
3. 启动计时器跟踪持续时间

## 阶段 2：认证（如需要）

**如果用户指定了认证凭据：**

```bash
$B goto <login-url>
$B snapshot -i                    # 找到登录表单
$B fill @e3 "user@example.com"
$B fill @e4 "[已编辑]"            # 永远不要在报告中包含真实密码
$B click @e5                      # 提交
$B snapshot -D                    # 验证登录成功
```

**如果用户提供了 cookie 文件：**

```bash
$B cookie-import cookies.json
$B goto <target-url>
```

**如果需要 2FA/OTP：** 询问用户提供验证码并等待。

**如果 CAPTCHA 阻止了你：** 告诉用户："Boss，请在浏览器中完成 CAPTCHA，然后告诉我继续。"

## 阶段 3：定位

获取应用地图：

```bash
$B goto <target-url>
$B snapshot -i -a -o "$REPORT_DIR/screenshots/initial.png"
$B links                          # 映射导航结构
$B console --errors               # 着陆页有错误吗？
```

**检测框架**（在报告元数据中记录）：
- `__next` 在 HTML 中或 `_next/data` 请求 → Next.js
- `csrf-token` meta 标签 → Rails
- `wp-content` 在 URL 中 → WordPress
- 客户端路由无页面刷新 → SPA

**对于 SPA：** `links` 命令可能返回很少的结果，因为导航是客户端的。使用 `snapshot -i` 查找导航元素（按钮、菜单项）。

## 阶段 4：探索

系统化访问页面。在每个页面：

```bash
$B goto <page-url>
$B snapshot -i -a -o "$REPORT_DIR/screenshots/page-name.png"
$B console --errors
```

然后按照**逐页探索清单**：

1. **视觉扫描** — 查看带注释的截图，找布局问题
2. **交互元素** — 点击按钮、链接、控件。能用吗？
3. **表单** — 填写并提交。测试空值、无效值、边界情况
4. **导航** — 检查所有进出路径
5. **状态** — 空状态、加载中、错误、溢出
6. **控制台** — 交互后有新的 JS 错误吗？
7. **响应式** — 如果相关，检查移动端视口：
   ```bash
   $B viewport 375x812
   $B screenshot "$REPORT_DIR/screenshots/page-mobile.png"
   $B viewport 1280x720
   ```

**深度判断：** 在核心功能（首页、仪表盘、结账、搜索）上花更多时间，在次要页面（关于、条款、隐私）上花更少时间。

**快速模式：** 只访问首页 + 定位阶段的前 5 个导航目标。跳过逐页清单——只检查：加载？控制台错误？可见的断链？

## 阶段 5：文档记录

发现每个问题时**立即记录**——不要批量处理。

**两级证据层：**

**交互 bug**（流程中断、按钮失效、表单提交失败）：
1. 操作前截图
2. 执行操作
3. 截图显示结果
4. 使用 `snapshot -D` 显示什么改变了
5. 写复现步骤，引用截图

```bash
$B screenshot "$REPORT_DIR/screenshots/issue-001-step-1.png"
$B click @e5
$B screenshot "$REPORT_DIR/screenshots/issue-001-result.png"
$B snapshot -D
```

**静态 bug**（拼写错误、布局问题、图片缺失）：
1. 拍一张带注释的截图显示问题
2. 描述什么不对

```bash
$B snapshot -i -a -o "$REPORT_DIR/screenshots/issue-002.png"
```

**每发现一个问题立即写入报告**。

## 阶段 6：总结

1. **使用下方量表计算健康评分**
2. **写"最需修复的 3 件事"** — 3 个最严重的问题
3. **写控制台健康摘要** — 汇总所有页面看到的控制台错误
4. **更新严重性计数**
5. **填写报告元数据** — 日期、持续时间、访问页面数、截图数量、框架
6. **保存基线** — 写 `baseline.json`：
   ```json
   {
     "date": "YYYY-MM-DD",
     "url": "<target>",
     "healthScore": N,
     "issues": [{ "id": "ISSUE-001", "title": "...", "severity": "...", "category": "..." }],
     "categoryScores": { "console": N, "links": N, "visual": N, "functional": N, "ux": N, "performance": N, "content": N, "accessibility": N }
   }
   ```

**回归模式：** 写完报告后，加载基线文件。比较：健康评分差异、已修复的问题（在基线但不在当前）、新增的问题（在当前但不在基线）。在报告中附加回归部分。

## 健康评分量表

计算每个类别的分数（0-100），然后取加权平均。

### 控制台（权重：15%）
- 0 错误 → 100
- 1-3 错误 → 70
- 4-10 错误 → 40
- 10+ 错误 → 10

### 链接（权重：10%）
- 0 断链 → 100
- 每个断链 → -15（最低 0）

### 分类评分（视觉、功能、用户体验、内容、性能、无障碍）
每个类别起始 100 分。按发现扣分：
- 关键问题 → -25
- 高问题 → -15
- 中问题 → -8
- 低问题 → -3
最低 0 分。

### 权重分配
| 类别 | 权重 |
|------|------|
| 控制台 | 15% |
| 链接 | 10% |
| 视觉 | 10% |
| 功能 | 20% |
| 用户体验 | 15% |
| 性能 | 10% |
| 内容 | 5% |
| 无障碍 | 15% |

### 最终评分
`score = Σ (category_score × weight)`

## 框架特定指南

### Next.js
- 检查控制台是否有水合错误（`Hydration failed`、`Text content did not match`）
- 监控 `_next/data` 请求中的 404
- 测试客户端导航（点击链接，不仅仅是 `goto`）——捕获路由问题
- 检查 CLS（累积布局偏移）

### Rails
- 检查控制台中的 N+1 查询警告（开发模式）
- 验证表单中的 CSRF token
- 测试 Turbo/Stimulus 集成
- 检查 flash 消息

### WordPress
- 检查插件冲突（不同插件的 JS 错误）
- 验证登录用户的 admin bar 可见性
- 测试 REST API 端点（`/wp-json/`）
- 检查混合内容警告

### 通用 SPA（React、Vue、Angular）
- 使用 `snapshot -i` 做导航——`links` 命令会漏掉客户端路由
- 检查过时状态（导航离开再回来——数据刷新了吗？）
- 测试浏览器前进/后退——应用正确处理了历史记录吗？
- 检查内存泄漏

## 重要规则

1. **复现是一切。** 每个问题至少需要一张截图。无例外。
2. **记录前验证。** 重试一次确认可复现，不是偶发。
3. **永远不包含凭据。** 复现步骤中密码写 `[已编辑]`。
4. **增量写入。** 发现问题立即追加到报告。不要批量处理。
5. **永远不读源代码。** 作为用户测试，不是开发者。
6. **每次交互后检查控制台。** 视觉上不显现的 JS 错误仍然是 bug。
7. **像用户一样测试。** 使用真实数据。完整走完工作流。
8. **深度胜过广度。** 5-10 个有充分证据的问题 > 20 个模糊描述。
9. **永远不删除输出文件。** 截图和报告是累积的。
10. **截图要展示给用户。** 每次 `$B screenshot` 或 `$B snapshot -a -o` 命令后，使用 Read 工具读取输出文件，让用户能内联看到截图。
